# Building the models

ONNX model weights for super-resolution upscaling, frame interpolation and low-light
enhancement, converted from
upstream PyTorch checkpoints for use with [StreamDock](https://streamdock.net).

Covers these model families (others, such as RealBasicVSR, AnimeSR and the audio models, are
described in their export scripts' docstrings):

- **Real-ESRGAN** (`esrgan/`) -- super-resolution upscaling, general-purpose and anime
- **Real-CUGAN** (`cugan/`) -- super-resolution upscaling, anime/general, three denoise levels
- **HAT** (`hat/`) -- super-resolution upscaling, transformer-based, high quality
- **RIFE 4.25** (`rife/`) -- frame interpolation for true N-times temporal upscaling, one
  model for every resolution
- **HVI-CIDNet** (`hvicidnet/`) -- low-light enhancement, any resolution
- **Face models** (`facedetect/`, `facerestore/`) -- YuNet face detection; GFPGANv1.4 face restoration

All models are generated by the export scripts in this directory, which download the
original checkpoints from upstream GitHub releases and convert them to ONNX with
DirectML-compatible dynamic-batch support.

The upstream model weights and architectures remain the intellectual property of their
original authors. See [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) for full license
and attribution details.

scale, pipeline type, source class, and descriptive tags.

### Upscaling ONNX conversion details (ESRGAN / CUGAN / HAT)

- **Opset**: 17
- **Input shape**: `[N, 3, 128, 128]` (N = batch size, dynamic) -- except HAT which uses `[N, 3, 64, 64]`
- **Output shape**: `[N, 3, tile*scale, tile*scale]`
- **Tile size**: 128x128 px for ESRGAN / CUGAN; 64x64 px for HAT (window_size=16 constraint)
- **Batch axis**: Dynamic (`N` symbolic dimension)
- **DirectML compatibility**: `Resize` nodes that use static size tensors are rewritten to
  use relative scales so DirectML recomputes correct buffer sizes at runtime regardless of N.

## RIFE 4.25 Frame Interpolation Model

RIFE (Real-Time Intermediate Flow Estimation) generates intermediate frames, matching a
stream's frame rate to the display refresh rate (e.g. a 30 fps stream on a 120 Hz monitor ->
4x multiplier, 3 interpolated frames per source pair).

| File | Resolution | Size | Upstream source |
|------|------------|-----:|-----------------|
| `rife/rife425.onnx` | any (dynamic height/width) | ~22.8 MB | `flownet_v4.25.pkl` from the [HolyWu/vs-rife model release](https://github.com/HolyWu/vs-rife/releases/tag/model), byte-identical to the 4.25 `train_log/flownet.pkl` linked from [hzwer/Practical-RIFE](https://github.com/hzwer/Practical-RIFE) |

RIFE 4.25 takes a `timestep` input, so it produces a frame at any t in (0, 1) rather than
only the midpoint, which is what true N-times interpolation needs.

### Why one model now covers every resolution

The previous RIFE (4.18) exports were fixed-shape, one ONNX per resolution tier. The
architecture was never the reason: the old exporter computed the backwarp grid
(`[1, 2, H, W]`) and the flow divisor from the export resolution and baked them into the graph
as constant buffers, so each file only ran at the size it was traced at.

`export_rife425_onnx.py` builds both in `forward()` from the padded input shape, using `arange`
rather than `linspace` so the exporter emits a `Range` over a dynamic dimension instead of
folding a constant. Every `F.interpolate` in the flow blocks uses `scale_factor`, which exports
as `Resize` with constant scales and stays dynamic, and `GridSample` (opset 16+) does the warp.
ONNX Runtime's CPU, DirectML and CUDA providers run the result at any size.

### Tensor interface

| Name | Shape | Contents |
|------|-------|----------|
| `img0` | float32 `[1, 3, H, W]` | first frame, RGB, 0..1 |
| `img1` | float32 `[1, 3, H, W]` | second frame, RGB, 0..1 |
| `timestep` | float32 `[1, 1, H, W]` | every element = t in (0, 1); 0 -> img0, 1 -> img1 |
| `output` | float32 `[1, 3, H, W]` | the frame at time t, RGB, 0..1 |

H and W are any positive size; batch is 1. The model reads only the timestep's value, so the
caller may fill it with one constant.

### Padding

4.25 has five flow blocks with scale list `[16, 8, 4, 2, 1]`; the first downsamples by 16
and then strides by 4, so the padded size must be a multiple of 64 (4.18's four blocks needed
32). The graph does this itself: the frames are zero-padded on the right and bottom to a
multiple of 64 (what upstream Practical-RIFE and vs-rife do), the timestep is edge-padded, and
the output is cropped back to H x W. The caller need not pad; a caller that already zero-pads
to 32 gets bit-for-bit the same frame as one that does not pad.

`scale` is fixed at 1.0 (upstream's default; upstream suggests 0.5 for 4K). `ensemble` is not
supported by RIFE 4.21 and later.

## Low-light Enhancement Model (HVI-CIDNet)

HVI-CIDNet (Yan et al., "HVI: A New Color Space for Low-light Image Enhancement", CVPR 2025)
brightens under-exposed footage. It maps RGB into the HVI colour space, enhances intensity and
colour in two branches, and maps back. The output is the finished image, not curve
parameters.

| File | Resolution | Size | Upstream source |
|------|------------|-----:|-----------------|
| `hvicidnet/hvi-cidnet.onnx` | any (dynamic height/width) | ~7.9 MB | `model.safetensors` from [Fediory/HVI-CIDNet-Generalization](https://huggingface.co/Fediory/HVI-CIDNet-Generalization) |

### Checkpoint choice

Upstream publishes several checkpoints, most trained on one benchmark dataset each.
StreamDock uses **Generalization**: trained on LOLv2-Synthetic with random gamma
augmentation, it is the one upstream recommends for real-world input (its demo's default),
where the per-benchmark checkpoints are tuned to one dataset's exposure and noise.
`--checkpoint sice` builds the SICE-trained variant as `hvi-cidnet-sice.onnx`; it is not
published.

### Tensor interface

| Name | Shape | Contents |
|------|-------|----------|
| `input` | float32 `[1, 3, H, W]` | RGB, 0..1, any H and W >= 8 |
| `output` | float32 `[1, 3, H, W]` | enhanced RGB, 0..1, same H and W |

Batch is fixed at 1. Cost and memory grow roughly linearly with H x W.

### Padding is inside the graph; do not tile

The network downsamples three times by 0.5, so it needs a multiple of 8. The graph
reflect-pads the frame on the bottom and right to a multiple of 8 (what upstream `eval.py`
and `app.py` do on the host), runs, clamps to [0, 1] and crops back. The caller must **not**
pad: a black border added outside the graph would be treated as picture and darken the edges.

Run it on the **whole frame, never in tiles**. The enhancement depends on the frame's global
brightness and colour, so tiles processed separately come out with different exposure and the
seams show.

### Export-time patches

The exporter replaces a few upstream methods with equivalents that compute the same values,
and checks the patched model against unpatched upstream before export:

- `RGB_HVI.HVIT` / `PHVIT` write through boolean masks, which export as data-dependent
  `NonZero`/`ScatterND`; they are rewritten as `torch.where` chains in the same precedence.
  `PHVIT` also clamps the hue sector to 0..5: upstream turns pixels whose hue rounds to
  exactly 1.0 black.
- `CAB.forward`: `einops.rearrange` becomes `reshape` (same memory order), so einops is not
  needed.
- `IEL.forward`: `tanh` is written via `exp`, because ONNX Runtime's DirectML provider fuses
  Conv + Tanh into a kernel that gives wrong output on these depthwise convs.

## Obtaining the models

### Via the build scripts (recommended)

Models are no longer bundled in the CI release zip. End users download them on first
launch via the in-app Model Manager, which reads URLs from `src/Configuration/Models/model-bundle.json`.

To build and publish a new set of models to the package registry (e.g. after an upstream
weight update), run:

```powershell
# Build all ONNX files and upload to the package registry
src\Scripts\build_and_upload_models.ps1 -Token <personal-access-token>

# Build locally without uploading
src\Scripts\build_and_upload_models.ps1 -LocalOnly
```

This script creates a Python venv, runs all export scripts, and uploads the results to
the GitLab package registry under `streamdock-models/<version>/`. It also patches
`src/Configuration/Models/model-bundle.json` with the resulting URLs, SHA-256 hashes, and
sizes.

### Building individual models locally

The export scripts live in this directory alongside the model files. They are fully
self-contained: they download both the architecture source files and the `.pth` checkpoints
directly from the upstream GitHub repositories. Temporary files (downloaded weights, arch
source) are cleaned up automatically after export; pass `--keep-tmp` to retain them.

### Real-ESRGAN models (x4plus, x2plus, animevideov3)

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxsim numpy onnxruntime

python export_esrgan_onnx.py [--out esrgan] [--models all|x2plus|x4plus|animevideov3] [--no-simplify]
```

`patch_esrgan_resize.py` is a standalone predecessor to `export_esrgan_onnx.py`. Its
dynamic-batch patching logic is fully integrated into `export_esrgan_onnx.py` and the file
is retained for reference only.

### Real-CUGAN models

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxruntime onnxsim

python export_cugan_onnx.py [--out cugan] [--models all|no-denoise|conservative|denoise3x] [--no-simplify]
```

### HAT model (hat-real-sr-x4-sharper)

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxsim numpy onnxruntime gdown

python export_hat_onnx.py [--out hat] [--models all|x4sharper] [--no-simplify]
```

Weights are downloaded from Google Drive via `gdown`. If the automatic download fails due
to rate limits, download `Real_HAT_GAN_sharper.pth` manually from the
[HAT model zoo](https://drive.google.com/drive/folders/1HpmReFfoUqUbnAOQ7rvOeNU3uf_m69w0)
and place it in `hat/_hat_export_tmp/`, then re-run (the script skips existing files).

### RIFE 4.25 model

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxruntime numpy

python export_rife425_onnx.py [--out rife] [--work DIR] [--keep-tmp] [--no-check]
```

Downloads the vs-rife architecture files at a pinned commit and `flownet_v4.25.pkl` (checked
against a pinned SHA-256), exports `rife/rife425.onnx` as one self-contained file, and compares
ONNX Runtime against PyTorch at aligned and unaligned sizes. The published file was built with
torch 2.12.0+cpu. CPU-only PyTorch is sufficient.

### HVI-CIDNet model

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxscript onnxruntime numpy safetensors

python export_hvicidnet_onnx.py [--out hvicidnet] [--checkpoint generalization|sice] [--gamma G] [--cache DIR] [--no-simplify]
```

Downloads four upstream source files at a pinned commit and the checkpoint at a pinned Hugging
Face revision into `~/.cache/hvicidnet`, both verified against pinned SHA-256 digests. When
`onnxruntime-directml` is installed, the sanity check also compares DirectML against CPU. The
published file was built with torch 2.15 and the default `--gamma 1.0` (no gamma curve).

### YuNet face detection model

`facedetect/face_detection_yunet_2023mar.onnx` is distributed pre-built from the
[opencv_zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)
repository. There is no local export script -- the file is bundled directly.

### Face restoration model (GFPGANv1.4)

```
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install onnx onnxsim numpy

python export_facerestore_onnx.py [--out facerestore] [--models all|gfpgan] [--no-simplify]
```

Outputs a fixed-shape `[1, 3, 512, 512]` model. No GPU needed.

> **Why `--no-simplify` / `dynamo=False`?** PyTorch 2.6+ defaults to the new dynamo
> exporter which splits weights into a separate `.onnx.data` file. `dynamo=False` (used
> internally by the script) keeps the legacy TorchScript path which embeds all weights
> inline, as expected by OnnxRuntime's single-file load.

Existing files are skipped, so the script is safe to re-run.
